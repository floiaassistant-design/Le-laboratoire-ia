# EXP-005 — l'ordre des tests ciblés a-t-il de l'importance ?

## Hypothèse enregistrée avant exécution

Sur les 16 programmes QuixBugs déjà utilisés dans EXP-004B, les premiers tests ciblés sélectionnés manuellement peuvent être moins informatifs que d'autres tests ciblés du **même ensemble figé**. Une permutation uniformément aléatoire des 12 mêmes entrées peut donc augmenter le nombre d'erreurs détectées lorsqu'on limite le budget à 1, 3 ou 6 entrées.

L'EXP-005 est une **analyse exploratoire** sur les mêmes programmes, pas une validation indépendante, et n'entraîne aucun agent ou modèle IA.

## Plan

1. Réutiliser exactement les 12 entrées par fonction de `edge_probes` (EXP-004B), sans modifier les valeurs, la fonction ni le nombre de tentatives.
2. Charger séparément les versions corrigée et défectueuse. Exécuter **une seule fois chaque entrée** par programme, avec copies indépendantes des arguments. Une entrée invalide côté référence consomme un emplacement du budget mais ne révèle pas de défaut.
3. Conserver, pour chaque entrée, les états oracle/version défectueuse (OK, exception, délai) et l'indicateur booléen « défaut exposé ».
4. Comparer **l'ordre d'origine** à 256 permutations uniformes préétablies, avec graines fixes, à budgets `1, 3, 6, 12`. Les mêmes 256 permutations sont réutilisées pour tous les budgets d'un même programme, assurant une progression des budgets emboîtée.
5. Calculer aussi la probabilité **exacte** pour une permutation uniforme et un budget de k parmi 12 entrées, dont d révèlent une anomalie :

\[
P(\mathrm{détecter}) = 1 - \frac{\binom{12-d}{k}}{\binom{12}{k}}
\]

Si `12-d < k`, le numérateur vaut zéro. Si `d=0`, la probabilité vaut zéro. Cette formule est une propriété combinatoire classique : elle **ne constitue pas une innovation algorithmique**.

6. Indiquer pour chaque budget : le nombre de programmes détectés dans l'ordre original, l'espérance exacte du nombre de programmes détectés après permutation aléatoire, l'écart-type combinatoire sous indépendance des permutations par programme, et la distribution simulée min, max, 10e/90e percentiles.
7. Journaliser les 16 programmes, y compris les cas sans détection et les erreurs ; ne masquer aucun échec de worker. Aucun changement des règles après consultation des résultats.

## Validité scientifique et limites

- Les 16 programmes sont déjà connus ; les **256 permutations ne constituent pas 256 nouveaux défauts**. Une comparaison sur le même corpus ne prouve pas une amélioration généralisable.
- L'ordre original (et la sélection des cas ciblés) provient d'un choix manuel ; la politique permutée utilise précisément les mêmes cas, mais cela ne la transforme pas en politique « intelligente ».
- Les résultats du candidat sur les 12 entrées sont mesurés une seule fois, puis **réutilisés** dans les simulations : cela suppose une sortie déterministe sur ces entrées ; les variations de temps et de timeout inter-exécutions ne sont pas évaluées.
- Le délai de 30 ms par appel vient d'EXP-004B. Une exception ou un délai de la version défectueuse n'est une anomalie que si la version corrigée fournit une sortie valide.
- Aucun usage des fixtures canoniques pour choisir les 12 entrées ; la connaissance des bogues de QuixBugs était néanmoins disponible avant le protocole.
- Ne pas classer la méthode permutée comme nouvelle meilleure stratégie. Toute sélection optimisée des ordres devrait être évaluée sur des défauts **distincts et indépendants**.

## Reproduire

```bash
python -m unittest discover -s tests -v
python -m lab.quixbugs_order
```

Le résultat complet s'enregistre dans `results/exp005.json`. Le rapport résumé est conservé sur GitHub et les détails d'exécution archivés via GitHub Actions. Aucun appel API facturé ni tâche planifiée.


## Résultats vérifiés EXP-005 (CI n° 41598473940)

| Budget | Ordre initial : programmes détectés | Ordre uniformément permuté : espérance exacte | 10e–90e centile empirique, 256 permutations |
|---:|---:|---:|---:|
| 1 | 0/16 | 8,33/16 | 6 à 10 |
| 3 | 11/16 | 12,46/16 | 11 à 14 |
| 6 | 12/16 | 14,70/16 | 13 à 16 |
| 12 | 16/16 | 16/16 | 16 |

La **même liste de 12 tests ciblés par programme** a été utilisée dans les deux conditions. Aucun nouveau cas n'a été ajouté. Les 16 programmes ont été évalués, aucun test de référence n'a été rejeté et les 39 tests unitaires ont réussi.

Les 256 permutations ne sont pas 256 bogues indépendants. Ce résultat montre l'importance de l'ordre de nos tests ciblés sur **ces défauts connus**, pas la supériorité d'une méthode intelligente de réorganisation ni l'efficacité d'agents IA. Les statistiques sont **exploratoires**. Le résultat complet et les comptes par programme sont dans `results/exp005-summary.json`. Les observations détaillées ont été enregistrées en artefact `exp005-order-raw` du run GitHub (conservation temporaire).

**Prochaine question :** apprendre ou prédéfinir un ordre de test sans consulter les défauts à détecter, puis vérifier sur de nouveaux programmes réellement indépendants. Ne pas choisir un ordre ici et revendiquer ensuite une validation sur ces 16 mêmes programmes.
